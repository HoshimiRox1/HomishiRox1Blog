# Responsive Layout Thresholds

## 模块性质

- 类型：通用响应式设计约束文档。
- 实现状态：已沉淀，供后续页面参考和复用。
- 冻结状态：半冻结；阈值可继续微调，但修改前要说明受影响页面和回归点。

## 目标

本文件记录 Roxy Blog 当前已验证过的响应式分段方式，以及“关联元素必须共用同一条缩放轨迹”的设计原则，避免后续页面再次出现：

- 卡片本体已经停住，但标题字号还在继续变大。
- 头像框、标题、footer 偏移各自使用不同的 `vw / clamp / min / max` 规则，导致错位。
- 平板态和手机态之间存在无人维护的尴尬过渡区间。

## 当前分段

### 全站最小宽度：`360px`

- 这是当前全站的硬下限，小于 `360px` 不再继续压缩页面布局。
- 实现基线位于 `src/styles.css` 的 `body { min-width: 360px; }`。
- 后续页面如果新增独立容器、全屏舞台或自定义 shell，不能绕过这条下限。

### 桌面：`min-width: 981px`

- 继续使用桌面白板 / 桌面导航 / 桌面舞台布局。
- 允许绝对定位构图。
- 如果一组元素属于同一视觉单元，例如身份卡、头像框、标题和底部 meta chips，它们必须从同一组响应 token 派生尺寸。

### 平板过渡：`831px - 980px`

- 允许进入单列流式阅读，但仍保留“平板过渡态”的留白和较大标题。
- 这是一个需要单独设计的区间，不能简单套桌面，也不能完全套手机。
- 当前 Profile 已在这个区间使用单列 whiteboard 流。

### 手机：`max-width: 830px`

- 进入移动端状态。
- 使用移动端导航变量：更窄的边框、更小的底部菜单占位、更紧凑的 HUD。
- 本次调整把旧的 `760px` 手机阈值提高到 `830px`，原因是 `830px - 760px` 之间原先仍走平板态，出现明显错位和阅读拥挤。

## 关键原则

### 1. 同一视觉单元只允许一套响应轨迹

如果这些元素在视觉上被读成一个整体，它们应该由同一组 token 控制：

- 卡片宽度
- 头像框尺寸
- 标题字号
- 相关说明文案宽度
- 与该卡片绑定的 footer / chip 偏移

不要让卡片宽度用 `min()`，标题字号用另一条 `clamp()`，头像再依赖 `aspect-ratio + auto stretch` 自己长。

### 2. 尽量先定义 token，再喂给组件

当前 Profile 桌面白板已采用：

- `src/utils/profileResponsive.js`

其中统一定义：

- `--profile-card-width`
- `--profile-avatar-size`
- `--profile-identity-title-size`
- `--profile-footer-offset`

后续页面如果也有“主卡 + 附属元素”的联动缩放，应优先照这个模式做，而不是在 CSS 里散落多个独立公式。

### 3. 过渡区间必须是被设计过的

如果某个区间没有单独维护价值，不要硬保留一个技术性断点。直接把它并入更稳定的下一种状态更安全。

这次 Profile 的 `830px - 760px` 问题就是典型例子：

- 平板规则还能生效
- 手机规则还没接管
- 最终导致布局“理论可用、视觉错位”

所以直接把手机阈值提到 `830px`，比继续补丁式修这个窄区间更可靠。

- `830px - 980px` 作为平板流式阅读区，保持单列 whiteboard。
- 桌面自由拖动类交互优先使用 pointer 驱动位移，不混用原生 HTML5 `draggable`，避免拖拽虚影和交互分裂。

## 开发前置约束

- 任何涉及响应式布局、断点、字号联动、卡片缩放、导航切换阈值的开发，都要先阅读本文件，再开始写样式或组件逻辑。
- 如果某次改动需要新增断点，先判断它是否会破坏现有 `360px / 830px / 980px` 分段语义，再决定是否引入。
- 如果只是为了修一个窄区间错位，不要先加断点，优先判断能否并入现有分段或复用联动 token。

### Home

- 标题、提示卡、人物舞台如果继续联动，优先抽成一组 token。

### Portfolio

- 如果后续有作品主画面、编号、技术标签和说明条，应该把它们作为一个“展示单元”统一缩放。

### Blog

- 如果会做书架 / 索引卡 / 分栏系统，先定义在哪个阈值切成单列，而不是等错位后再补救。
